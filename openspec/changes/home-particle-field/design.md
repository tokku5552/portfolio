## Context

トップページの Hero は CSS の `Orb` で構成されていた。Twilight Blade の規約（brand.md）は「グラデーションは indigo→violet→pink のみ」「アクセントは 1 画面に 1 つ」「JS アニメーションライブラリを使わない」を定めている。CLAUDE.md も依存を最小に保つ方針をとっている。

表現の方向性は、A〜D の 4 案（液体状の Orb / オーロラ / パーティクル / ブレード）のプロトタイプを見比べて、C（パーティクル）に決めた。その後、Hero だけでなくページ全体に広げ、セクションごとに形を変える方針に拡張した。

## Goals / Non-Goals

**Goals:**

- 同じ粒がページ全体を通してついてきて、セクションごとに形を変える体験にする
- 依存を追加しない
- WebGL が使えない環境・JS が無効な環境・reduced-motion の環境でも、表示を崩さない
- 本文やカードの読みやすさを損なわない

**Non-Goals:**

- マウス追従やホバーへの反応（スクロール連動のみ）
- トップページ以外への導入
- WebGL コンテキストを失ったあとの復帰

## Decisions

### 1. 素の WebGL1 と自作シェーダで実装する

- 採用: WebGL1 / GLSL ES 1.00、依存なし。
- 代替案: three.js（約 150KB 増）、React Three Fiber（さらに大きい）。点群を描くだけなら素の WebGL で足り、依存最小の方針にも合う。WebGL2 は対応環境を狭める割に得るものがない。

### 2. canvas は 1 枚で、形の切り替えは頂点シェーダでブレンドする

- 採用: ページ全体に canvas を 1 枚置く。各粒は 5 つの形すべてでの位置を頂点シェーダで計算できるようにし、float の `u_stage` の整数部で形 A、次の整数で形 B を選んで、小数部でブレンドする。切り替えの途中では `sin(πf)^2` に比例して外側へ散らし、「ほどけてから次の形になる」動きにする。
- 代替案: セクションごとに canvas を置く方式。作りは単純だが、WebGL コンテキストが増え（ブラウザの上限は約 16）、セクションをまたいだつながりも出ない。

### 3. 精度は「頂点シェーダ highp、フラグメントシェーダ mediump でバリイングのみ」

- ノイズや色の計算はすべて頂点シェーダ（既定で highp）で行う。フラグメントシェーダは varying だけを受け取る。こうすると VS と FS で同じ uniform を共有せずに済み、精度の不一致によるリンクエラーが起きない（プロトタイプで実際に発生した）。モバイル GPU で mediump のハッシュノイズが崩れる問題も避けられる。

### 4. 重なり順は「absolute の層の中に sticky の canvas」

- 採用: `Home.page.tsx` でコンテンツを `div.relative` で包む。最初の子として `ParticleField`（`absolute inset-0`）を置き、その中に `sticky top-0 h-lvh` の canvas を置く。コンテンツは兄弟要素として `relative z-[1]` にする。
- 代替案 1: `position: fixed`。positioned 要素は非 positioned なフッターより上に描画されるため、フッターを覆ってしまう。
- 代替案 2: sticky 要素に負の margin-bottom を付けて高さを打ち消す方式。sticky は margin box で親に収まろうとするため、負の margin のぶん親からはみ出し、フッターを覆った（実装中に確認）。
- `lvh` を使う理由: `dvh` はモバイルの URL バーの開閉で高さが変わる。高さが変わると canvas のサイズを付け直すことになり、描画バッファがクリアされる。

### 5. スクロール位置から形の番号への変換は純関数にする

- `computeStage(anchors, scrollY, viewportHeight)` を `stage.ts` に置く。アンカーはセクション上端の document 上の位置と形の番号の組で、文書順にチェーン状にブレンドする。次のセクションの上端がビューポートの 0.55 に達したら切り替えを始め、0.3 ビューポート分で終える。Works のような短いセクションが常に切り替え途中に見えないよう、切り替えの範囲をビューポートの上半分に寄せている。
- アンカーの位置は ResizeObserver（canvas の層・コンテンツ・body）で測り直し、毎フレームの処理は算術だけにする。body も観測するのは、モバイルのヘッダーメニューのように、コンテンツ自体の大きさを変えずに全セクションを押し下げる変化を拾うため。
- ページを開いた直後の 0.6 秒は追従率を 1 にして、スクロール位置の復元やハッシュへの移動で途中の形を経由しないようにする。

### 6. CSS Orb を段階的強化の土台として残す

- Hero の `Orb` は SSR の HTML に必ず含める。`ParticleField` が最初のフレームを描いたら `onActiveChange(true)` で知らせ、Hero 側で `invisible opacity-0` にする（visibility を外すことで、ぼかしたアニメーションの描画コストも消える）。WebGL が使えない場合と、コンテキストを失った場合は Orb のままになる。

### 7. ブランド規約は改訂して例外を明記する

- brand.md の「アクセントは 1 画面に 1 つ」と「ドット模様の背景の禁止」は、この表現と文言レベルで衝突する。そこで規約を改訂し、`ParticleField` を唯一の例外として明記した。アクセントは Hero の形だけで、他のセクションの形は暗く抑える（強さは Hero の 0.42 倍、格子は 1 点に粒が重なるため 0.22 倍）。

### 8. dispose ではコンテキストを破棄しない

- React StrictMode では、開発時に effect が同じ canvas で 2 回実行される。cleanup で `loseContext()` を呼ぶと、2 回目の `getContext` が使えないコンテキストを返して代替表示に落ちる。そのため、dispose ではバッファ・プログラム・シェーダだけを削除する。代償として、`/` と他ページを行き来すると、切り離された canvas のコンテキストが GC されるまで残る。

## Risks / Trade-offs

- [トップページ表示中は描画ループが止まらない] → 対策: `powerPreference: 'low-power'`、モバイルは 6,000 粒・DPR 1、ソフトウェア描画では使わない。バックグラウンドタブではブラウザが rAF を止める。IntersectionObserver による停止も検討したが、コンテンツがページ全体に広がっていて画面外に出ないので効果がなく、外した。
- [粒数と DPR はマウント時に固定] → 回転や窓の大きさの変更で狭い画面と広い画面をまたいでも、配置はシェーダが canvas の大きさ（CSS px 換算）から判定し直す。粒数だけは再マウントまで変わらない。
- [reduced-motion の設定変更やブラウザのズームによる DPR の変化に追従しない] → 再読み込みで反映される。頻度が低いので許容する。
- [追従率がフレームレートに依存する（120Hz では収束が 2 倍速）] → 見た目の差は小さいので許容する。
- [アクセントのグラデーションがページ全体に広がる] → ブランド規約を改訂して明記し、Hero 以外の強さを抑えた。
